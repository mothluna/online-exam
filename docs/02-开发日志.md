## 二、决策记录

### D-001 为什么放弃 Docker 官方镜像源，改用前缀拉取

守护进程配置了 `docker.1ms.run`、`docker.xuanyuan.me`、`docker.m.daocloud.io` 三个镜像源。实测 `xuanyuan` 持续返回"免费节点繁忙"，`1ms.run` 对 `minio/*` 返回 not found，只有 `daocloud` 稳定。

改 `daemon.json` 需要重启 Docker Desktop，而本环境的 Docker 启动依赖 `wsl.exe`（被安全策略拦截，只能用户手动启动），重启成本高且可能失败。因此选择不改配置，用**前缀拉取 + 重命名**绕开：

```bash
docker pull docker.m.daocloud.io/library/mysql:8.0.36
docker tag  docker.m.daocloud.io/library/mysql:8.0.36 mysql:8.0.36
```

代价是每次清空镜像后都要手动执行，已写入 `deploy/README.md`。

### D-002 MinIO 归档后的技术选型

`dl.min.io` 对 MinIO Server / Client / KES 一律返回 **410 Gone**，声明"项目已归档，不再提供下载与安全更新"；Docker Hub 与 quay.io 的镜像同样不可得。

评估三个方向：① 继续找 MinIO 旧镜像（来源不可信，且违反"不使用来路不明镜像"的安全底线）；② 换本地文件系统实现（偏离课题"文件存储 MinIO"）；③ 换 S3 兼容服务。

选 ③ RustFS：S3 API 完整兼容，**Java 侧仍使用 MinIO SDK（io.minio），业务代码零改动**，仅 endpoint 指向不同。将来若取得 MinIO 镜像，改 `OBJECT_STORAGE_IMAGE` 一行即可切回，迁移成本可控。

**利害（补充说明，验收会被追问）**：

- **利**：对象存储链路真实可用（建桶、上传、预签名下载均已实测），业务代码与 `StorageService` 抽象零改动，切换被压缩到一行环境变量。
- **害**：① 严格说没用 MinIO Server，与题目字面要求有偏差，必须主动说明而不是蒙混；② 没有 MinIO Console 与 `mc` 工具链，排障手段变少；③ RustFS 较新，生产案例与长期稳定性背书远不如 MinIO；④ 只用到了 put/get/presign 等基础能力，分片上传、版本控制、生命周期这些边界行为未验证——也就是说**"S3 兼容"这句只在项目实际用到的子集内成立**。
- **边界**：这不是选型变更，是部署层替换。若评审要求必须是 MinIO Server，回退动作是改镜像与环境变量，不需要改代码；但需自行解决镜像来源的可信问题（这正是当前绕开的原因）。

设计文档侧同步写在 `01-需求分析与方案设计` 2.6.1，避免只有开发日志里有解释、需求文档仍写"MinIO"造成前后不一致。

### D-003 JDK 21 → 17 的切换方式

`JAVA_HOME` 与 `PATH` 都指向 `D:\develop\jdk\current`，而 `current` 是指向 `jdk-21.0.12.1+1` 的 **junction**。

考虑三种切法：① 装 JDK 17 后改用户 `JAVA_HOME` + `PATH`——两处都要改，容易漏；② 用 Maven toolchain——Maven 仍跑在 21 上，`java -version` 依旧是 21，验收时说不清；③ 重指 junction。

选 ③：`current` 改为指向 `jdk-17.0.2` 后，`JAVA_HOME`、`PATH`、Maven、IDE 全部自动跟随，只改一处且完全可逆（指回 21 即可）。JDK 21 目录保留未删。

> 注意：删除 junction 用 `[IO.Directory]::Delete(path, $false)`，**不能用 `Remove-Item -Recurse`**，后者在部分 PowerShell 版本上会顺着链接删掉目标目录内容。

### D-004 统一响应为什么要自己拦 404

Spring 6.1 起，无匹配 handler 时抛 `NoResourceFoundException` 而不是走默认错误页。若 `@RestControllerAdvice` 里只写了 `@ExceptionHandler(Exception.class)` 兜底，这个异常会被吞成 **500**——接口写错路径时前端看到的是"服务器错误"，排查方向完全被带偏。

因此必须为它单独建档返回 404。这条也解释了为什么"全局异常处理"不能只写一个兜底，兜底越宽，越容易把客户端错误伪装成服务端错误。

### D-005 401 与 403 的判定必须流水线化

题目要求"越权访问返回 403"。这里有个容易做反的地方：**越权的前提是已认证**。若把"没有令牌"也判成 403，前端就无法区分"该去登录"和"该提示无权限"，用户会卡在一个永远点不动的页面上。

所以拦截器把校验拆成有序的四步，前三步任何一步失败都是 401（身份不成立），只有第四步失败才是 403（身份成立但权力不够）：

```
验签 → 白名单 → 版本号 → 角色
40101   40102     40102    40300
```

实现上刻意**不用 Spring Security 的过滤器链**：它默认的 `AuthenticationEntryPoint` / `AccessDeniedHandler` 是在过滤器层抛错，与 `@RestControllerAdvice` 的异常出口是两套机制，很容易出现"异常处理器没生效、返回默认 HTML 错误页"的情况。用 `HandlerInterceptor` 抛 `BizException`，异常统一走 `GlobalExceptionHandler`，状态码与响应体格式只有一处出口。

### D-006 版本号的数据库与缓存必须同时改

`auth_version` 存在 `sys_user` 表里，但每个请求都查库代价太高，所以缓存 24 小时。这里埋着一个陷阱：**只 `UPDATE` 数据库而不刷新缓存，旧令牌最长还能用 24 小时**——"改密后全端下线"就成了一句空话。

因此把"递增版本"封装成 `bumpAuthVersion`，内部同时做三件事：读当前值 → 更新数据库 → 覆盖 Redis。

```java
userMapper.updateById(update);
redis.opsForValue().set(RedisKey.authVersion(userId), String.valueOf(next), VERSION_CACHE);
```

调用方（改密、改角色、强制下线）只允许调这个方法，不允许自己拼 SQL。这条约束写进接口注释，避免后来者绕过去。

### D-007 题干归一化是"不可逆承诺"

`stem_hash` 是唯一索引的一部分，一旦上线，**归一化规则就不能再改**——改了以后历史题目的 hash 与新算法不一致，同一个题干会算出两个指纹，去重直接失效。

所以规则在设计时就写死并集中在一个类里（`StemNormalizer`），只有五个步骤：

```
去首尾空白 → 压缩连续空白 → 全角转半角 → 标点统一 → 英文小写 → 去首尾标点 → SHA-256
```

实测"下列哪个是接口关键字？"与"  下列哪个是接口关键字?  "（全角问号 + 前后空格）被判为同一题干，返回 409 并给出已有题目的 ID。反过来，"1+1=2"与"1+1=3"不会被误判，因为数字不同。

如果将来必须调整规则，正确做法是加版本号（`stem_hash_v2`）并离线重算，而不是直接改函数体。

### D-008 为什么列表不返回答案和解析

两个理由，缺一不可：

1. **安全**：教师端列表如果带答案，抓包就能拿到整库答案；学生端将来共用 VO 时更容易出事。
2. **性能**：`analysis` 是 TEXT，20 条一页看起来不多，但题干+解析一起回表，网络传输和堆内存都要翻倍。

做法是列表查询用 `wrapper.select(...)` 显式排除 `analysis`，VO 里 `answer` 只在详情接口赋值。实测列表响应中 `"answer"` 出现次数为 0。

### D-009 导入为什么必须"分批预检 + 分批插入"

最直觉的写法是每行一次 `insert`，靠唯一索引拦重复。问题有三个：

1. **性能**：1000 行就是 1000 次数据库往返，即使本地也要 3~5 秒，网络稍差就逼近 30 秒红线；
2. **异常当流程控制**：重复是"预期内的常见情况"，用 `DuplicateKeyException` 来表达既慢又会污染事务；
3. **定位困难**：批量插入失败时，异常信息只给一个键值，无法直接对应到 Excel 第几行。

因此改成三段式：

```
逐行解析 → 攒够 500 条 → 一条 IN 查询预检 → 一条多值 INSERT 落库
```

- 1000 行只需 **2 次查询 + 2 次插入**；
- 冲突行在预检阶段就被识别，直接进失败明细，不产生异常；
- 真正的并发冲突（预检与插入之间被别的请求插队）由 `uk_stem_hash` 仲裁，捕获后降级为逐条插入，精确定位到行。

实测：1000 行（含 50 条重复）服务端 **585~745ms**，总耗时 0.60~0.76s，距 30 秒红线有 40 倍余量。

### D-010 失败明细的行号不能"事后补"

第一版把冲突行记在 flush 阶段，只存了题干没存行号，结果二次导入时，预览的前 20 条全是"文件内重复"（逐行阶段发现），而真正与库冲突的 480 条排在后面且行号为空——用户看到"500 条失败"却只能看到 20 条重复提示，完全无法定位。

修正的核心是**让缓冲的行携带 Excel 行号**（`PendingRow(rowNo, question)`），并在输出前按行号排序。这条经验可以推广：**任何延迟处理的错误，都必须当场捕获定位信息**，否则事后无从还原。

### D-011 抽题为什么不用 `ORDER BY RAND()`

最省事的写法是给每条规则拼一句 `... ORDER BY RAND() LIMIT n`，但它在 MySQL 里是**全表生成随机数再排序**，执行计划必带 `Using temporary; Using filesort`，耗时随题池线性增长；题池到十万级时单条规则就要几秒，而一张卷有四五条规则。

改成"取 id → 内存洗牌"：

```sql
SELECT id FROM question WHERE status=1 AND type=? [AND category_id IN (...)] [AND difficulty=?]
```

只扫覆盖索引，把 id 拉进内存后用 `Collections.shuffle` 取前 n 个。950 道题池实测抽 42 题 **50ms**，其中大部分是建连与两次 SQL 的开销。

### D-012 "总分偏差为 0"落在哪三个点

这句话很容易被理解成"算总分时小心一点"，实际需要三处同时成立：

| 时机 | 动作 | 不做的后果 |
|---|---|---|
| 保存规则 | `Σ(数量 × 每题分值) == 设定总分`，不等直接拒绝并给出差额 | 一张注定 98 分的卷子能存进去，后面全靠人眼发现 |
| 抽题 | 先查题池是否够，不够**整卷失败**，不做"能抽多少抽多少" | 缺 3 题 → 总分少 6 分，偏差静默产生 |
| 发布 | 再查一次 `COUNT/SUM(paper_question)` 与 `paper` 声明值比对 | 有人手工改了库、或历史脏数据，错误卷子仍能发出去 |

三处都做，才谈得上"偏差为 0 是结构保证"。实测把 `paper.total_score` 从 4000 改成 4001 后发布，被拒绝并明确报出"实际 40.00 分，与设定 40.01 分不一致"。

### D-013 手工组卷为什么不校验"设定总分"

规则组卷的总分是**推导值**（来自规则），手工组卷的总分是**汇总值**（来自已选题）。对后者强行要求"先填总分再凑题"会逼教师反复调分，体验很差。

做法是：每次加题/移题后立刻 `recomputeTotals`，把 `paper.total_score/count` 重算一遍。这样"声明值"与"事实值"在任何时刻都相等，发布校验天然通过；一旦有人绕过接口改库，发布时仍会被 D-012 的第三道检查拦住。

### D-014 唯一键为什么是 (exam_id, user_id, seq_no)

设计文档里写的是 `uk_exam_user(exam_id, user_id)`，但 `exam` 表还有一个 `allow_retake` 字段——两者直接冲突：唯一键一旦生效，重考就永远插不进去。

三种解法：

| 方案 | 问题 |
|---|---|
| 去掉 allow_retake，一律不许重考 | 功能缺失，且字段留着是误导 |
| 重考时覆盖原答卷 | 历史成绩丢失，统计口径崩坏 |
| 唯一键加上 seq_no | 允许重考时 seq_no 递增；不允许时永远插 1，第二次自然撞键 |

选第三种。`allow_retake=0` 时插入逻辑固定用 `seq_no=1`，唯一键照样是"同一考生一场考试只有一份答卷"；`allow_retake=1` 时取 `max(seq_no)+1`，历史答卷完整保留。

代价是唯一键从两列变三列，拦截语义要靠服务层保证"不重考时 seq_no 恒为 1"——已写死在 `start()` 里，只有一处。

### D-015 开考的三层防护

```
Redis SETNX（10s）  →  唯一键仲裁  →  状态判断
   挡并发点击            最终正确性        已交卷/已超时提示
```

第一层只是省一次数据库冲突的成本，**正确性完全由第二层保证**。曾经想过只做第一层，但 Redis 抖动、锁过期、多实例都会让它失效，而 `DuplicateKeyException` 是数据库级别的事实。

实测 20 并发同一考生开考：`1×200 + 19×409`，库中恰好 1 条答卷。

409 响应会带回 `{"attemptId": 1, "status": "IN_PROGRESS"}`，前端拿到后直接跳续考页，而不是弹一个"你已开考"然后让用户自己找入口。

### D-016 交卷为什么必须 CAS + afterCommit

**CAS**（`WHERE status='IN_PROGRESS' AND version=?`）：重复提交时第二次 `affected=0`，直接读回既有结果。如果不做，两个并发请求都会往下走判分逻辑，分数可能翻倍。

**afterCommit**：缓存清理放在事务提交之后。若在事务内删 Redis，一旦后续语句回滚，就出现"缓存已删、库里还是旧状态"的短暂不一致；虽然能自愈，但期间读到的状态是错的。

**幂等实测**：连续两次交卷，`submitTime` 完全相同（`17:27:03`），说明第二次没有重新走流程。

### D-017 超时任务只能捞"已过期"的

写第一版时加了个 `scanOnce()` 便于测试，实现是"遍历全部 `IN_PROGRESS` 直接置 TIMEOUT"——如果它被误调用（或被当成定时任务），**正在答题的考生会被集体强制交卷**，而且不可恢复。

这个方法是自己 review 时删掉的。保留的版本只有一条取数条件：

```sql
SELECT id FROM exam_attempt WHERE status='IN_PROGRESS' AND deadline < NOW(3) LIMIT 200
```

并且逐条走 CAS，与考生主动提交竞争时以先到者为准。实测把 deadline 改到 5 秒前，30 秒内状态变为 `TIMEOUT`，`submit_time` 精确等于 `deadline`（不是任务执行时刻），这样统计出的作答时长才准确。

### D-018 整数分值还不够，取整方式也要"对称"

题目要求"边界分数判定正确，无浮点误差"。用 int 存 0.01 分解决了浮点问题，但**除法取整引入了新的不公平**。

第一版填空和简答都是"每份平分 + 最后一个吃余数"：

```
1000 分 / 3 个关键词 → 每个 333，最后一个 334
命中第 3 个关键词 → 334 分
命中第 1 个关键词 → 333 分
```

同样是"命中 1 个"，得分却不同，取决于命中位置。这在评卷时无法解释，学生申诉也站不住。

单元测试第一次跑就撞出了这个问题（我原本的用例断言 666，实际 333，回头一看是规则本身不对称）。改成统一的比例式：

```java
if (hits == total) return fullScore;      // 全对直接满分，避免取整差 1 分
return fullScore * hits / total;          // 其余按比例，向下取整
```

这样"命中数相同则得分相同"，且全对必然精确等于满分。填空 200 分 3 空答对两空也从 132 变成 133（`200×2/3`）。

### D-019 主观题只做"粗筛"，不能算终评

关键词命中率能解决"大面积空白/完全跑题"的批量初筛，但它读不懂语义：学生用同义表述答对了，一样得 0 分。

因此主观题的结果刻意做成三件事：

1. `judge_type = UNJUDGED`（不是 AUTO），与客观题的自动判分区分开；
2. `judge_detail` 记录命中了哪几个词，教师一眼能看出机器为什么给这个分；
3. 提交结果里 `needReview = true`，前端必须提示"待教师复核"。

这样即使规则分不准，也不会变成"系统的最终结论"。

### D-020 一条聚合 SQL 而不是五个子查询

统计列表需要每场考试的开考数、提交数、平均分、最高分、最低分、及格数。直觉写法是六个标量子查询，或者先查考试再逐个 `count`——两种都是 N+1。

实际采用"一次扫描 + 条件聚合"：

```sql
SELECT exam_id,
       COUNT(*) AS joinCount,
       SUM(status <> 'IN_PROGRESS') AS submitCount,
       ROUND(AVG(CASE WHEN status <> 'IN_PROGRESS' THEN total_score END)) AS avgScore,
       MAX(CASE WHEN status <> 'IN_PROGRESS' THEN total_score END) AS maxScore,
       MIN(CASE WHEN status <> 'IN_PROGRESS' THEN total_score END) AS minScore,
       SUM(status <> 'IN_PROGRESS' AND is_pass = 1) AS passCount
FROM exam_attempt
WHERE exam_id IN (...)     -- 长度等于页大小，与总记录数无关
GROUP BY exam_id
```

一次扫描拿到全部指标，配合 `idx_exam_status_score(exam_id, status, total_score)` 覆盖索引。

另外把"考试分页"和"试卷总分"合成一个 JOIN，避免多一条批量查试卷的 SQL——这样整个列表接口严格 3 条：

```
① count 考试  ② 分页考试(JOIN paper)  ③ 本页 exam_id 聚合
```

实测 21 场考试 / 1903 份答卷，P95 **19ms**；1001 条成绩明细 P95 **22ms**，深分页第 50 页 P95 **13ms**。

### D-021 一个"假监控"的自我了断

为了证明"SQL 条数为常数级"，我写了个 MyBatis 拦截器，把每请求执行的语句数记到 ThreadLocal，再在访问日志里打出 `sql=N`。

结果是：**日志一直显示 `sql=0`**，而接口明明查了库。

排查发现两个问题叠加：① 这套 MyBatis-Plus 组合下插件并没有被稳定应用（全程只命中过一次）；② 即便命中，ThreadLocal 与过滤器读取之间也没对上。我试了改成写 `HttpServletRequest` attribute，仍是 0。

这时候有两个选择：继续调拦截器，或者承认这条路走不通。选了后者——**一个恒为 0 的监控比没有监控更危险**，它会让后来者以为"每请求 0 条 SQL"。

替换方案不需要写任何代码：MyBatis 自己会按 traceId 打印 `==> Preparing:`，直接数日志即可。

```bash
curl -s -D - -o /dev/null ".../stats/exams" | grep -i X-Trace-Id
grep <traceId> app.log | grep -c "Preparing:"
```

实测三个接口（含深分页）每请求都恰好 3 条。证据可复核、代码零侵入，比自建拦截器更可靠。

### D-022 所有"权限相关变更"都必须递增版本号

用户管理里有五个操作会改变"这个令牌还能不能代表这个人"：

| 操作 | 为什么必须失效旧令牌 |
|---|---|
| 改角色 | 令牌里写着 `role=TEACHER`，不改就还是教师权限，降级形同虚设 |
| 重置密码 | 密码都换了，旧会话没有理由继续有效 |
| 停用 | 账号已停用，但已登录的人还能继续答题直到令牌过期（最长 2 小时） |
| 强制下线 | 这是该功能的本体 |
| 删除账号 | 行没了，版本查询自然返回 `TOKEN_REVOKED`，无需额外处理 |

前四个统一走 `authService.bumpAuthVersion(id)`，一处实现、全部生效。实测改角色后旧令牌立刻 `401/40102`，停用后连登录都被拒。

**删除是唯一例外**，而且踩了个坑：一开始删除后也调 `bumpAuthVersion`，结果它去查已删除的用户、抛 `NOT_FOUND`，整个事务回滚——删用户永远失败，报 404。原因是"递增版本"这个动作本身需要用户行存在。

正确做法是删除后什么都不做：令牌校验时 `selectAuthVersion` 查不到人，会走 `TOKEN_REVOKED` 分支。**同一个"让令牌失效"的目标，删除场景靠的是"查无此人"，而不是版本号。**

### D-023 自保护比功能本身更重要

管理后台最容易被做成"能把自己锁在门外"。三个保护写死在服务层：

- 不能停用自己 → 否则下次登录被拒，只能改库
- 不能修改自己的角色 → 管理员把自己降成学生，就再没有人能改回来
- 不能删除自己

外加一条兜底：**至少保留一个可用的管理员**。停用、降级、删除管理员时都会 `count(role=ADMIN and status=1)`，等于 1 就拒绝。

这三条不是"锦上添花"，而是验收时一定会被问到的边界：如果系统能被管理员一键搞死，那它就是不可运维的。

### D-024 导出为什么分两条路径

一个导出接口要同时满足"小数据立刻给文件"和"大数据不把请求线程占死"，只能分流：

| 行数 | 路径 | 响应 |
|---|---|---|
| ≤ 5000 | 直接写 `response.getOutputStream()` | 200 + xlsx 文件流 |
| > 5000 | 提交到专用线程池，写临时文件后上传对象存储 | 202 + `taskId` |

前端拿 202 后轮询 `/export-stats/{taskId}`，`DONE` 时拿到预签名链接。用状态码区分而非在 body 里塞 `mode` 字段，客户端一眼就能判断该渲染文件还是渲染进度条。

**流式的关键在分批写。** 用 `ExcelWriter` + `WriteSheet` 每 500 行 `write()` 一次，而不是 `doWrite(List)`：

```java
long offset = 0;
while (true) {
    List<AttemptExportRow> rows = statMapper.exportRows(examId, offset, BATCH);
    if (rows.isEmpty()) break;
    writer.write(rows, sheet);
    offset += rows.size();
    if (rows.size() < BATCH) break;
}
```

内存里始终只有 500 行，与总行数无关。异步路径同样分批写进临时文件，最后再整体读入上传——这一步是唯一的规模上限（万级行约几 MB），已在代码注释中写明若要支持十万级需改分片上传。

**任务表放内存**（`ConcurrentHashMap`）是明确的取舍：单实例部署够用，重启后未完成任务丢失；多实例或需要持久化时应换成数据库或 Redis。这类取舍写在代码注释里，比藏在文档里更容易被后来者看到。

实测 6001 行：接口 **15ms** 返回 202，任务 **280ms** 完成，文件 6002 行 / 248KB。

### D-025 两个踩在"看起来没问题"上的坑

**① MySQL 客户端字符集导致中文双重编码。**

压测数据用 `docker exec mysql < seed.sql` 导入，会话 `character_set_client=latin1`，于是 `压` 的 UTF-8 字节被当成 latin1 字符再存一遍，取出来就是 `åŽ‹æµ‹`。

症状很隐蔽：**接口返回 200、数据行数正确、程序不报错**，只有中文变成乱码。修复方法是在脚本首行 `SET NAMES utf8mb4`，存量数据用 `CONVERT(BINARY(CONVERT(col USING latin1)) USING utf8mb4)` 反向还原。

顺带一条判据：Java 写入的中文正常、SQL 导入的中文乱码 → 问题在客户端连接，不在应用。

**② `username` 与 `userName` 在 MyBatis 里是同一个 key。**

导出 SQL 同时选了 `u.username AS username` 和 `u.real_name AS userName`。MyBatis 的结果集自动映射按**大小写不敏感**匹配列名，两个别名撞在一起，后写的覆盖前者，导致"姓名"整列为空。

程序不报错、列数正确、只是值是 null——属于最难查的一类问题。改法很简单：别名用 `realName`，并在字段上留注释说明为什么不能叫 `userName`。

这条经验有普适性：**SQL 别名不要造只差大小写的两个词**，人看着没问题，映射器看着是同一个。

### D-026 请求层不能直接 import router

最开始想在 axios 拦截器里 `import router from '@/router'`，401 时直接跳登录页。但依赖会成环：

```
request → router →（守卫里用 store）→ store → api → request
```

ESM 能容忍循环，只要不在模块初始化阶段取值；但这类"能跑但脆弱"的结构不该留在基座里——后面加一个拦截器就可能 `undefined`。

改成依赖注入：

```ts
// request.ts
let unauthorizedHandler: (() => void) | null = null
export function setUnauthorizedHandler(h: () => void) { unauthorizedHandler = h }

// main.ts（唯一知道 router 与 store 的地方）
setUnauthorizedHandler(() => {
  useUserStore().clear()
  router.replace({ path: '/login', query: { redirect: router.currentRoute.value.fullPath } })
})
```

请求层只负责"通知有人 401"，怎么处理由装配层决定。归属清晰，也没有环。

### D-027 Element Plus 先全量引入

首版 `app.use(ElementPlus)` 全量注册，主包 **1.28MB / gzip 416KB**。按需引入（`unplugin-vue-components` + `ElementPlusResolver`）能压到 1/4 左右，但：

- `ElMessage` / `ElMessageBox` 这类函数式组件的样式不会被组件解析器自动带上，需手动引 style；
- 现在四个业务页面都还没写，此时优化等于对着空壳调优。

所以先全量、把功能跑通，页面齐了再统一换按需引入并复测体积。这个取舍记在这里，免得后面被当成"没做优化"。

### D-028 一套表单承载五类题型，而不是五个表单

五类题型的差异集中在"答案输入"：单选是 radio、多选是 checkbox、判断是二选一、填空按空分行、简答是关键词。如果拆成五个弹窗，公共字段（分类、题干、解析、难度、分值、状态）要复制五遍，改一个校验规则要改五处。

做法是**一个表单 + 按 `type` 切换答案控件**：

```
题型变更 → 清空答案相关字段（避免残留上一题型的答案被误提交）
选择题  → 选项编辑区显示，答案从选项 key 里选
判断    → 固定两选项
填空    → 一行一个空，| 分隔同空多种写法
简答    → 逗号分隔关键词
```

两个容易漏的细节：

- **删除选项时同步清理答案**。否则多选题的答案里残留 `C`，而选项只剩 A/B，提交会被后端判为"答案不在选项中"。
- **切题型必须清空答案**。radio 的值残留在 `singleAnswer` 里，切成多选后不会被提交，但切回来会带着旧值，用户看着像"系统帮我选了"。

### D-029 前端的状态回滚不是可选项

表格里的启用/停用是一个 `el-switch`，绑定的是行数据。用户点一下，UI 立刻变了，然后才发请求。如果请求失败（403、网络中断、题目已被别人删除），**界面会显示"已停用"而库里还是启用**。

所以 `toggleStatus` 里必须回滚：

```ts
try {
  await changeQuestionStatus(row.id, target)
} catch {
  row.status = target === 1 ? 0 : 1   // 立刻改回去
}
```

同类问题还有删除分类后左侧树的选中态：分类删掉了，右侧还在按已删除的 id 过滤，列表会是空的，用户以为"数据丢了"。所以删除成功后要清掉 `selectedCategoryId` 并重载列表。

**乐观更新本身没问题，问题是只做"更新"不做"回滚"。**

### D-030 总分前端算一遍，后端还要再算一遍

规则编辑区实时显示「规则合计 60.00 分 / 27 题，与设定总分一致」，不一致时标红并禁用保存。

看起来是重复劳动——后端 `buildRules` 已经校验了。但两边目的不同：

- **前端**是为了"不让用户白填"。填完 6 条规则再点保存、被拒、回头找哪条错了，体验很差；实时对账能在输入过程中就指出差 70 分。
- **后端**是唯一可信的判定。前端算的是"界面上的数字"，后端算的是"将要入库的数据"，而且 `PUT` 接口可以直接被调用，绕过一切前端校验。

所以前端算完不能把结果当作"已经校验过"传上去，仍然原样提交规则，由后端复算。实测前端规则合计 60.00 分时，后端返回的也是 60.00 分——两边算法必须一致（都是 `数量 × 每题分值` 求和，再用两位小数收口），否则会出现"前端绿、后端红"的诡异状态。

**一个容易被忽略的点：浮点。** `2.5 × 3 + 3.3` 在 JS 里可能得到 `10.799999999999999`，直接用 `===` 判断会永远不相等。前端同样用 `toFixed(2)` 收口再比较，与后端 `int` 分值的思路对齐。

### D-031 预览按题型分组，而不是只给总数

抽完题只显示"27 题 / 60 分"是够用的，但看不出**规则有没有被正确执行**——万一把多选的 5 题抽成了单选，总分可能仍然对得上，问题却被掩盖。

所以详情页在题目列表上方加了一行分组统计：

```
单选 10 题 / 20.00 分   判断 10 题 / 10.00 分
多选 5 题 / 20.00 分    填空 2 题 / 10.00 分
```

一眼就能对照规则表确认"每种题型抽了几题、占多少分"。实测与规则完全一致（10/10/5/2，20/10/20/10）。

另外，题目表格保留了 `sortNo`（卷内序号），这是考试时题目顺序的权威来源——抽题时若开启乱序，顺序在这一步就写进 `attempt_answer.sort_no` 了。

### D-032 倒计时必须以服务端时间为准

前端拿到的 `deadline` 是服务端算好并落库的，但如果直接用 `deadline - 本机当前时间`，改一下系统时钟就能"续命"。

所以后端在 `AttemptVO` 里额外返回 `serverTime`，前端启动时算一次偏差：

```ts
clockOffset = parseTime(serverTime) - Date.now()
remaining  = deadline - (Date.now() + clockOffset)
```

这样即使本机时间快 10 分钟，倒计时也按服务端的 20 分钟走。改本机时钟只会让这个偏移一直存在，仍然拿不到额外时间。

**另一个细节：** 闭合标签页、切后台时 `setInterval` 会被浏览器节流（后台可能 1 分钟才触发一次），但 `remaining` 每次都由真实时间差算出来，所以只会"跳秒"，不会算错；一旦归零就立即自动交卷。反过来如果按"每次减 1"来倒计时，节流会导致时间凭空变多。

### D-033 自动暂存的三个触发点与失败回队

作答页有两条保存路径，目的不同：

| 触发 | 时机 | 目的 |
|---|---|---|
| 防抖 800ms | 停止输入后 | 用户答题时尽快落库，避免崩溃丢答案 |
| 定时 10 秒 | 周期 | 兜底，防止长文本输入过程中一直不触发 |
| 交卷前 flush | 点击交卷 | 保证最后几秒的改动也进库 |

三者都走同一个 `flush()`，内部做了两件关键的事：

1. **先取走 dirty 再发请求**。`const ids = [...dirty]; dirty.clear()`，请求期间用户继续输入的新题号会进入新的 dirty 集合，不会被这次请求"顺手清掉"。
2. **失败放回队列**。`catch` 里 `ids.forEach(id => dirty.add(id))`，下一轮 10 秒会自动重试。如果直接丢弃，用户看到"已保存"却是假象。

另外 409（已提交/已超时）要单独处理：停止定时器并立即触发交卷，否则会每 10 秒弹一次错误提示。

### D-034 离开页面要拦两次，因为浏览器有两个出口

- **`beforeunload`**：拦关闭标签页、刷新、地址栏跳转，触发浏览器原生"确定离开？"弹窗（文案不可定制）。
- **`onBeforeRouteLeave`**：拦站内路由跳转（点侧边栏、点返回），可以弹 Element Plus 的确认框。

只做前者，站内跳转不拦；只做后者，直接关标签页会静默丢题（虽然已暂存的不会丢，但用户不知道）。

两者都要在 `result` 存在或状态不是 `IN_PROGRESS` 时自动失效，否则交卷完点"返回列表"还会再弹一次。

作答页因此**不套主框架布局**——考试期间侧边栏根本不该出现，少一个误点入口。

### D-035 图表为什么不用 ECharts

分数分布是一张十档柱状图，需求里没有折线、饼图、下钻、联动。为此引入 ECharts 的代价是：

- 主包再加 **约 1MB**（gzip 300KB+），而当前主包已经因为全量引入 Element Plus 到了 417KB；
- 需要处理按需引入、主题、自适应 resize 三件事；
- 图表配置项本身比这张图的业务逻辑还长。

所以用 **CSS 柱状图**：`flex` 布局 + 每根柱子的 `height: count/max*100%`，只有三十行样式。

```html
<div class="track"><div class="bar" :style="{ height: height(item.count) }" /></div>
```

好处是零依赖、随容器自适应、和 Element 的配色变量天然一致；代价是没有 tooltip / 缩放等交互（用原生 `title` 属性替代了 tooltip）。

**判断标准很简单：图表的交互复杂度是否超过实现它的成本。** 十档柱状图不值得，多轴折线就该上 ECharts 了。真到那一步，按需引入 `echarts/core` 只打 `BarChart` 也能控制体积。

### D-036 前端怎么区分"文件"和"任务"

同一个导出接口返回两种东西：小数据是 xlsx 二进制，大数据是 `202 + JSON`。前端不能靠状态码判断——axios 对 2xx 一律走成功分支，且 `responseType: 'blob'` 时 JSON 也会变成 Blob。

用 **Content-Type** 区分：

```ts
const contentType = String(response.headers['content-type'] ?? '')
if (contentType.includes('application/json')) {
  const text = await (response.data as Blob).text()   // Blob 要再读一次
  return { mode: 'task', ...JSON.parse(text).data }
}
return { mode: 'file', blob: response.data, filename }
```

两个坑：

1. **必须显式 `responseType: 'blob'`**，否则 axios 会按文本解析二进制，xlsx 直接损坏；反过来 JSON 也必须先 `Blob.text()` 才能 `JSON.parse`。
2. **文件名要从 `Content-Disposition` 里取**，且优先取 `filename*=UTF-8''` 那段——中文名只有这段是可靠的（另一段是 RFC 2047 编码，解出来是乱码）。

拿到 taskId 后轮询 `/export-tasks/{id}`，`DONE` 再 `window.open(presignedUrl)`。轮询上限 40 次（40 秒），超时提示"仍在处理"而不是无限等。

### D-037 危险操作让用户"说清楚再点"

用户管理里有四个操作会造成不可逆后果：

| 操作 | 后果 | 前端确认文案的重点 |
|---|---|---|
| 停用 | 对方立即掉线且无法登录 | 说清"会被强制下线" |
| 重置密码 | 所有设备掉线，旧密码失效 | 要求输两遍新密码，避免手滑打错把自己锁外面 |
| 强制下线 | 只掉线，不改任何数据 | 说明"需要重新登录"，不夸大后果 |
| 删除 | 数据不可恢复 | 明确提示"有答卷的用户无法删除，请改为停用" |

删用户的文案里直接写出限制，用户就不会点了才被拒。**把后端规则前置到确认框，是最省事的可用性改进。**

反过来，前端不做"这个能不能删"的预判（比如先查有没有答卷）——那样要多一次请求、还可能因并发失效。真正的判定永远在后端，前端只负责把规则说清楚、把拒绝原因展示出来。

### D-038 按需引入的收益要看全站，且必须同时处理四个"影子依赖"

D-027 里承诺"页面齐了再换按需引入"，这一步就是兑现。但 `app.use(ElementPlus)` 不只是注册组件，它还顺带承担了三件隐式职责，删掉主包会变小、页面会坏：

| 隐式职责 | 全量引入时的表现 | 按需后必须补什么 |
|---|---|---|
| 全局 locale | `app.use(ElementPlus, { locale: zhCn })` | 改用 `<el-config-provider :locale>` 包裹根节点（它用 `renderSlot` 渲染，不产生包装元素，不会打断 `height:100%` 链） |
| `v-loading` 指令 | 随全量注册一起注入 | 显式 `app.use(ElLoading)`；指令是运行期解析，不在模板组件扫描范围内 |
| 图标组件 | `import * as Icons` 全量注册 | 只注册实际用到的 16 个；菜单 icon 存的是字符串，靠 `<component :is>` 运行期解析，必须保留注册 |
| 函数式组件样式 | 全量 CSS 覆盖 | `ElMessage`/`ElMessageBox`/`ElLoading` 的样式不会被解析器自动带上，需手动引 `theme-chalk/el-*.css` |

**一个更要命的细节**：字符串形式的图标引用（`:prefix-icon="'Lock'"`）是运行期按组件名解析的，**漏注册只会静默失效，类型检查抓不到**。登录页密码框的锁图标就差点这样丢掉。已改成直接传组件引用 `:prefix-icon="Lock"`，让 `vue-tsc` 能兜住。

**收益必须按全站算，不能只看主包。** 按需后组件被拆成独立 chunk，主包从 1285.87KB 掉到 262.81KB 很有欺骗性——真实对比（同一台机器、同一份代码、stash 前后各构建一次）：

| | 全量 | 按需 | 变化 |
|---|---|---|---|
| JS gzip 合计 | 458.7 KB | 324.6 KB | −29.2% |
| CSS gzip 合计 | 55.0 KB | 47.2 KB | −14.3% |
| **全站 gzip 合计** | **513.7 KB** | **371.8 KB** | **−27.6%** |

没有降到"1/4"，原因是 D-035 提到的 Element Plus 之外，业务代码、Vue/Router/Pinia 本来就占大头，且 44 个组件里 table/tree/upload/date-picker 这类重组件几乎全用上了。**27% 是诚实的数字，写"压到 1/4"就是吹。**

顺带修了一笔类型债：组件有了真实类型后，`el-table` 插槽的 `row` 是 `DefaultRow`（`Record<PropertyKey, any>`），传给 `ExamItem` 一类窄类型参数会报错。之前全量注册时组件无类型、`row` 是 `any`，这批错被吞掉了。修法是在**调用边界显式收窄**（每个页面一个 `asXxx(row)` 函数），而不是在模板里写 `as`——模板断言在 P-05 已经记过不可靠。

| P-15 | 简答题没有客户端字数提示 | 超长文本可能超出预期排版 | 加 `maxlength` 与字数统计；后端答案 JSON 本身无长度限制 |
| P-18 | 大数据导出完成后在轮询回调里 `window.open`，可能被浏览器拦截（脱离用户点击栈） | 用户点了导出却看不到文件 | 改为任务完成后展示"下载"按钮，由用户点击触发；或提前 `window.open('')` 占位再改 `location` |
| P-19 | 及格率在"提交数为 0"时显示 `0.0%`，与"全军覆没"无法区分 | 教师容易误读为全员不及格 | 前端在 `submitCount === 0` 时显示 `--`；后端 `passRate` 可返回 null |
| P-20 | 分布图按满分百分比分档，绝对分细节被抹平（60 分与 69 分同档） | 看不出临界分数的人堆在哪 | 需要时可加"按 5 分绝对区间"的第二张图，或允许切换分档方式 |
| P-22 | 用户列表没有批量操作（批量停用/批量重置） | 1000+ 考生时逐个点很慢 | 表格加 `type="selection"` + 后端批量接口；属于增强项，不在当前验收范围 |

### 3.3 一个值得单独说明的现象

实测中给判断题提交 `"B"`（非法值）时，后端不报错、判 0 分、状态照常流转。这条既是 P-11，也说明了一个设计取向：

**考试作答链路优先保证"不阻断考生"**——网络抖动、格式异常时宁可把答案原样存下来，也不要因为校验失败让考生无法继续答题。代价是脏数据可能入库，因此判分环节必须对未知取值做兜底（`singleChoice` 里 `correct.equals(user)` 天然返回 0）。

如果将来要做严格校验，也应该放在**交卷时**而不是**暂存时**：暂存失败会让考生卡住，交卷失败至少还能看到提示并修正。
