## 二、决策记录

### D-001 为什么放弃 Docker 官方镜像源，改用前缀拉取

守护进程配置了 `docker.1ms.run`、`docker.xuanyuan.me`、`docker.m.daocloud.io` 三个镜像源。实测 `xuanyuan` 持续返回"免费节点繁忙"，`1ms.run` 对 `minio/*` 返回 not found，只有 `daocloud` 稳定。

改 `daemon.json` 需要重启 Docker Desktop，而本环境的 Docker 启动依赖 `wsl.exe`（被安全策略拦截，只能用户手动启动），重启成本高且可能失败。因此选择不改配置，用**前缀拉取 + 重命名**绕开：

```bash
docker pull docker.m.daocloud.io/library/mysql:8.0.36
docker tag  docker.m.daocloud.io/library/mysql:8.0.36 mysql:8.0.36
```

代价是每次清空镜像后都要手动执行，已写入 `deploy/README.md`。

### D-002 MinIO 归档后的技术选型

`dl.min.io` 对 MinIO Server / Client / KES 一律返回 **410 Gone**，声明"项目已归档，不再提供下载与安全更新"；Docker Hub 与 quay.io 的镜像同样不可得。

评估三个方向：① 继续找 MinIO 旧镜像（来源不可信，且违反"不使用来路不明镜像"的安全底线）；② 换本地文件系统实现（偏离课题"文件存储 MinIO"）；③ 换 S3 兼容服务。

选 ③ RustFS：S3 API 完整兼容，**Java 侧仍使用 MinIO SDK（io.minio），业务代码零改动**，仅 endpoint 指向不同。将来若取得 MinIO 镜像，改 `OBJECT_STORAGE_IMAGE` 一行即可切回，迁移成本可控。

### D-003 JDK 21 → 17 的切换方式

`JAVA_HOME` 与 `PATH` 都指向 `D:\develop\jdk\current`，而 `current` 是指向 `jdk-21.0.12.1+1` 的 **junction**。

考虑三种切法：① 装 JDK 17 后改用户 `JAVA_HOME` + `PATH`——两处都要改，容易漏；② 用 Maven toolchain——Maven 仍跑在 21 上，`java -version` 依旧是 21，验收时说不清；③ 重指 junction。

选 ③：`current` 改为指向 `jdk-17.0.2` 后，`JAVA_HOME`、`PATH`、Maven、IDE 全部自动跟随，只改一处且完全可逆（指回 21 即可）。JDK 21 目录保留未删。

> 注意：删除 junction 用 `[IO.Directory]::Delete(path, $false)`，**不能用 `Remove-Item -Recurse`**，后者在部分 PowerShell 版本上会顺着链接删掉目标目录内容。

### D-004 统一响应为什么要自己拦 404

Spring 6.1 起，无匹配 handler 时抛 `NoResourceFoundException` 而不是走默认错误页。若 `@RestControllerAdvice` 里只写了 `@ExceptionHandler(Exception.class)` 兜底，这个异常会被吞成 **500**——接口写错路径时前端看到的是"服务器错误"，排查方向完全被带偏。

因此必须为它单独建档返回 404。这条也解释了为什么"全局异常处理"不能只写一个兜底，兜底越宽，越容易把客户端错误伪装成服务端错误。

### D-005 401 与 403 的判定必须流水线化

题目要求"越权访问返回 403"。这里有个容易做反的地方：**越权的前提是已认证**。若把"没有令牌"也判成 403，前端就无法区分"该去登录"和"该提示无权限"，用户会卡在一个永远点不动的页面上。

所以拦截器把校验拆成有序的四步，前三步任何一步失败都是 401（身份不成立），只有第四步失败才是 403（身份成立但权力不够）：

```
验签 → 白名单 → 版本号 → 角色
40101   40102     40102    40300
```

实现上刻意**不用 Spring Security 的过滤器链**：它默认的 `AuthenticationEntryPoint` / `AccessDeniedHandler` 是在过滤器层抛错，与 `@RestControllerAdvice` 的异常出口是两套机制，很容易出现"异常处理器没生效、返回默认 HTML 错误页"的情况。用 `HandlerInterceptor` 抛 `BizException`，异常统一走 `GlobalExceptionHandler`，状态码与响应体格式只有一处出口。

### D-006 版本号的数据库与缓存必须同时改

`auth_version` 存在 `sys_user` 表里，但每个请求都查库代价太高，所以缓存 24 小时。这里埋着一个陷阱：**只 `UPDATE` 数据库而不刷新缓存，旧令牌最长还能用 24 小时**——"改密后全端下线"就成了一句空话。

因此把"递增版本"封装成 `bumpAuthVersion`，内部同时做三件事：读当前值 → 更新数据库 → 覆盖 Redis。

```java
userMapper.updateById(update);
redis.opsForValue().set(RedisKey.authVersion(userId), String.valueOf(next), VERSION_CACHE);
```

调用方（改密、改角色、强制下线）只允许调这个方法，不允许自己拼 SQL。这条约束写进接口注释，避免后来者绕过去。

### D-007 题干归一化是"不可逆承诺"

`stem_hash` 是唯一索引的一部分，一旦上线，**归一化规则就不能再改**——改了以后历史题目的 hash 与新算法不一致，同一个题干会算出两个指纹，去重直接失效。

所以规则在设计时就写死并集中在一个类里（`StemNormalizer`），只有五个步骤：

```
去首尾空白 → 压缩连续空白 → 全角转半角 → 标点统一 → 英文小写 → 去首尾标点 → SHA-256
```

实测"下列哪个是接口关键字？"与"  下列哪个是接口关键字?  "（全角问号 + 前后空格）被判为同一题干，返回 409 并给出已有题目的 ID。反过来，"1+1=2"与"1+1=3"不会被误判，因为数字不同。

如果将来必须调整规则，正确做法是加版本号（`stem_hash_v2`）并离线重算，而不是直接改函数体。

### D-008 为什么列表不返回答案和解析

两个理由，缺一不可：

1. **安全**：教师端列表如果带答案，抓包就能拿到整库答案；学生端将来共用 VO 时更容易出事。
2. **性能**：`analysis` 是 TEXT，20 条一页看起来不多，但题干+解析一起回表，网络传输和堆内存都要翻倍。

做法是列表查询用 `wrapper.select(...)` 显式排除 `analysis`，VO 里 `answer` 只在详情接口赋值。实测列表响应中 `"answer"` 出现次数为 0。

### D-009 导入为什么必须"分批预检 + 分批插入"

最直觉的写法是每行一次 `insert`，靠唯一索引拦重复。问题有三个：

1. **性能**：1000 行就是 1000 次数据库往返，即使本地也要 3~5 秒，网络稍差就逼近 30 秒红线；
2. **异常当流程控制**：重复是"预期内的常见情况"，用 `DuplicateKeyException` 来表达既慢又会污染事务；
3. **定位困难**：批量插入失败时，异常信息只给一个键值，无法直接对应到 Excel 第几行。

因此改成三段式：

```
逐行解析 → 攒够 500 条 → 一条 IN 查询预检 → 一条多值 INSERT 落库
```

- 1000 行只需 **2 次查询 + 2 次插入**；
- 冲突行在预检阶段就被识别，直接进失败明细，不产生异常；
- 真正的并发冲突（预检与插入之间被别的请求插队）由 `uk_stem_hash` 仲裁，捕获后降级为逐条插入，精确定位到行。

实测：1000 行（含 50 条重复）服务端 **585~745ms**，总耗时 0.60~0.76s，距 30 秒红线有 40 倍余量。

### D-010 失败明细的行号不能"事后补"

第一版把冲突行记在 flush 阶段，只存了题干没存行号，结果二次导入时，预览的前 20 条全是"文件内重复"（逐行阶段发现），而真正与库冲突的 480 条排在后面且行号为空——用户看到"500 条失败"却只能看到 20 条重复提示，完全无法定位。

修正的核心是**让缓冲的行携带 Excel 行号**（`PendingRow(rowNo, question)`），并在输出前按行号排序。这条经验可以推广：**任何延迟处理的错误，都必须当场捕获定位信息**，否则事后无从还原。

### D-011 抽题为什么不用 `ORDER BY RAND()`

最省事的写法是给每条规则拼一句 `... ORDER BY RAND() LIMIT n`，但它在 MySQL 里是**全表生成随机数再排序**，执行计划必带 `Using temporary; Using filesort`，耗时随题池线性增长；题池到十万级时单条规则就要几秒，而一张卷有四五条规则。

改成"取 id → 内存洗牌"：

```sql
SELECT id FROM question WHERE status=1 AND type=? [AND category_id IN (...)] [AND difficulty=?]
```

只扫覆盖索引，把 id 拉进内存后用 `Collections.shuffle` 取前 n 个。950 道题池实测抽 42 题 **50ms**，其中大部分是建连与两次 SQL 的开销。

### D-012 "总分偏差为 0"落在哪三个点

这句话很容易被理解成"算总分时小心一点"，实际需要三处同时成立：

| 时机 | 动作 | 不做的后果 |
|---|---|---|
| 保存规则 | `Σ(数量 × 每题分值) == 设定总分`，不等直接拒绝并给出差额 | 一张注定 98 分的卷子能存进去，后面全靠人眼发现 |
| 抽题 | 先查题池是否够，不够**整卷失败**，不做"能抽多少抽多少" | 缺 3 题 → 总分少 6 分，偏差静默产生 |
| 发布 | 再查一次 `COUNT/SUM(paper_question)` 与 `paper` 声明值比对 | 有人手工改了库、或历史脏数据，错误卷子仍能发出去 |

三处都做，才谈得上"偏差为 0 是结构保证"。实测把 `paper.total_score` 从 4000 改成 4001 后发布，被拒绝并明确报出"实际 40.00 分，与设定 40.01 分不一致"。

### D-013 手工组卷为什么不校验"设定总分"

规则组卷的总分是**推导值**（来自规则），手工组卷的总分是**汇总值**（来自已选题）。对后者强行要求"先填总分再凑题"会逼教师反复调分，体验很差。

做法是：每次加题/移题后立刻 `recomputeTotals`，把 `paper.total_score/count` 重算一遍。这样"声明值"与"事实值"在任何时刻都相等，发布校验天然通过；一旦有人绕过接口改库，发布时仍会被 D-012 的第三道检查拦住。
